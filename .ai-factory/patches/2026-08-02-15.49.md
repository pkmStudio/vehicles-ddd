# Vehicles import/export S3 artifact paths and import report links

**Date:** 2026-08-02 15:49
**Files:** config/vehicles/export.php, config/vehicles/import.php, Vehicles Import reporting DTO/service/reporter, Vehicles Export file path builder, related tests
**Severity:** medium

## Problem

Vehicles import completion notifications with validation errors included a report path but did not include the storage disk. `dan-center` builds download actions only when both `path` and `disk` are present, so the user notification had no file link. Vehicles export and import artifacts also used different S3 key conventions, producing nested paths such as an export disk root plus an `exports/` directory while uploaded imports used `imports/dan-vehicles/...`.

## Root Cause

The import report workflow treated the saved CSV path as sufficient notification metadata, while the consumer contract required disk plus path. The path layout was split across env disk roots and hardcoded per-feature subdirectories, so changing a disk root could accidentally create duplicated folder segments.

## Solution

Vehicles import failure reports now use configurable `vehicles.import.failures.disk` and `vehicles.import.failures.directory`, defaulting to `s3` and `dan-vehicles/import`. The import completion DTO includes `disk` plus compatibility aliases `failures_report_disk` and `failures_report_path`. Vehicles export output defaults to `s3` and `dan-vehicles/export`, and the export path builder handles empty directories safely.

## Prevention

When publishing file artifacts for another service, tests must verify both the physical storage path and the full notification payload needed by the consumer to build a URL. Avoid combining business directory names with Storage disk roots unless the consumer contract explicitly documents both layers.

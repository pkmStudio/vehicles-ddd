# Removed broad dynamic PHPDoc types from engine modification import/export flow

**Date:** 2026-08-13 16:20
**Files:** Vehicles import/export factory contracts, factory implementations, queued import adapters, engine export service contracts
**Severity:** low

## Problem

New and recently touched import/export code contained overly broad PHPDoc value types after the
engine/modification import-export implementation. The project convention is to keep DTO and
boundary types explicit, so broad dynamic annotations should not be introduced.

## Root Cause

The implementation reused older project PHPDoc patterns with arbitrary array values and
overly broad serialization shapes. Those annotations were convenient for raw Excel and
Laravel Validator input, but the actual accepted values are narrower: scalar values, null, small
string lists, cache keys and typed import context DTOs.

## Solution

Replaced broad annotations in the new flow with explicit value unions and array shapes:

- factory inputs now document scalar/null/list-string values instead of arbitrary values;
- queued import serialization now documents exact `cacheKey`, `lockKey` and `ImportRunContextDTO`
  shapes;
- engine export row contracts now document scalar/null cell values;
- the reference-row closure now returns `?string` instead of an arbitrary value.

## Prevention

- During implementation, grep changed files for broad dynamic PHPDoc types before final verification.
- For raw rows, document the real accepted value set instead of falling back to arbitrary values.
- For `__serialize()`/`__unserialize()`, use exact array shapes with DTO/scalar/null fields.
- Avoid adding type-cleanup work to runtime logging: this is a static contract issue, not a
  production behavior fix.
